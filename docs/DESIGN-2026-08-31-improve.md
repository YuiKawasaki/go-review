## 調査で分かった前提

### 1. 解説がテンプレートだった原因（確定）

二重に塞がっていた。

- `anthropic` パッケージが未導入だった → このセッションで導入済み（`pip install anthropic` / SDK 1.2.0）
- `.env` の `ANTHROPIC_API_KEY` が**空文字**だった → **未対応。ユーザー本人が `.env` に設定する必要がある**

`config.py:132` の `claude_available` は「キーがある かつ CLAUDE_ENABLED」で判定するため、キーが空だと `explain.py:78` の `ClaudeClient` が常に利用不可となり、73問すべてが `template_explanation()` の穴埋め文で生成されていた。DBの実データで確認済み。

### 2. 手順再生の部品は既にある

`web/js/app.js:347` の `renderVariation()` が、棋譜画面で変化図を1手ずつ送るUIを持っている。練習画面・詰碁画面はこれを使っていないだけ。**共通部品に切り出して2画面へ流用できる。**

### 3. 誤答への咎め手順は、既存データからかなり作れる

`moves.candidates` 列に、各局面のKataGo候補手が **上位3手ぶん、それぞれ読み筋(pv)8手つき** で既に保存されている（`analysis.py:221`）。加えて `variations` テーブルに best（正解の進行）と punish（実戦の手への咎め）がある。

つまり既存73問について、**追加の解析なしで**次の点を押したときの手順が出せる。

- 正解手（best）
- KataGo候補の2〜3位の手
- 実戦で実際に打った手（punish）

→ 1問あたり最大5点ぶん。ここが今回の実装コストを大きく下げている。

## 実装計画

### A. 解説を分かりやすくする

#### A-1. APIキーの設定（ユーザー作業）

`.env` の `ANTHROPIC_API_KEY=` に自分のキーを書いてもらう。こちらでは鍵を扱わない。

**費用の見積り**（`claude-opus-5` / 入力 $5・出力 $25 per 1M tokens）

- 既存73問の再生成: 1問あたり入力約600・出力約1200トークン → **合計およそ $2.4（約350〜600円）の一回きり**
- 以後の新規問題: 1問あたり **5円前後**（1局につき最大3問なので、1局10〜15円）

`explain.py` の冒頭コメントにある「月額固定費0円」の要件からは外れる。ただし従量課金であり、解析しない月は0円。**キーを設定しない選択も可能**で、その場合は A-2 のテンプレート改良と A-4 のナレーションだけが効く（それでも今よりかなり読みやすくなる）。

#### A-2. プロンプトと文章構成の刷新（`go_review/explain.py`）

現行は「3見出し・全体400字以内」。これを変える。

- 対象読者を「級位者」と明示する。専門用語を使ったら**その場で短く言い換える**ことを必須にする
- 構成を4段にする
  1. **何が起きたか** — 用語なしで1〜2文
  2. **相手の狙い** — punish の読み筋の各手をなぞって説明する
  3. **なぜ正解手なのか** — best の読み筋に沿って
  4. **次に使える一言** — 似た場面で思い出すためのルール（例:「石を取りにいく前に、自分の石の呼吸点を数える」）
- 字数上限を 400字 → **700〜800字**へ
- `SYSTEM_PROMPT` の「初段前後の学習者に伝わる範囲」を「級位者に伝わる言葉。専門用語は必ず言い換えを添える」に変更
- 数値を事実として渡し、モデルに読みをさせない原則はそのまま維持する（`MoveContext.to_prompt()` は変更しない）
- `template_explanation()` も同じ4段構成に合わせて書き直す（キー未設定でも改善が効くように）

#### A-3. 全問再生成のCLI追加（`go_review/cli.py`）

```
python -m go_review regenerate-explanations [--only P-0001,P-0002] [--dry-run]
```

`problems` テーブルを走査して `generate_explanation()` を呼び直し、`explanation` を更新する。KataGo は使わないので解析バッチと同時に走らせられる。`--dry-run` で1問だけ出力して文章を確認してから全問へ流す。

#### A-4. 用語辞書（`web/js/glossary.js` 新規）

- `tagging.py` の `TAG_DESCRIPTIONS` を書き出したものを土台に、囲碁用語（中手・欠け眼・ゲタ・シチョウ・ウッテガエシ・オイオトシ・呼吸点・目・急所・ヨセ・アタリ・切り・ノビ・ハネ など）を追加する
- 解説文の描画時に用語を検出して下線つきの `<button class="term">` に置き換え、タップで意味を出す
- 長い語を先にマッチさせ、置換済みの範囲は二重置換しない
- `renderExplanation(text)` として `app.js` に置き、練習画面・詰碁画面の両方で使う

#### A-5. 盤面ナレーション

`variations.py:93` の `pv_comments()` が既に「石を取る・アタリにする・切る」といった事実を機械生成している。これを B の手順プレイヤーで1手ごとに表示する。LLM は使わないので費用ゼロ・オフラインでも動く。

### B. 手順を盤面で1手ずつ確認できるようにする

#### B-1. データ: `refutations` テーブルを追加（`go_review/db.py`）

```sql
CREATE TABLE IF NOT EXISTS refutations (
    problem_id  TEXT NOT NULL,   -- 練習問題は P-xxxx、詰碁は T-xxxx
    move        TEXT NOT NULL,   -- 学習者が打つ可能性のある手（GTP座標）
    kind        TEXT,            -- 'best'（正解） | 'candidate'（候補手） | 'actual'（実戦の手）
    pv_moves    TEXT,            -- JSON: その手のあとの進行（最大10手）
    pv_comments TEXT,            -- JSON: 各手の一言（pv_comments() の出力）
    winrate     REAL,            -- その手を打った直後の自分の勝率
    score       REAL,
    visits      INTEGER,         -- KataGo がこの手に割いた探索数
    PRIMARY KEY (problem_id, move)
);
```

既存DBには `ALTER`/追加テーブルとして入る（`db.py` は既に `PRAGMA table_info` でマイグレーションする作りなので、そこに合わせる）。

#### B-2. 埋め方

**既存73問**（再解析なし）
`moves.candidates` の上位3手 + `variations` の best / punish から組み立てる。`pv_comments()` を各PVに対して回してナレーションを付ける。KataGo 不要なので数分で終わる。

**新規に解析する局面**
`analysis.py:221` の `before.moves[:3]` を **`[:8]`** に広げ、`pv` の切り出しも `[:8]` → `[:10]` にする。解析コストは増えない（KataGo が既に返している情報を捨てているだけなので）。

**任意（承認をもらえれば）**
既存73問の局面だけを対象に `pass2_visits=1500` で1局面ずつ再解析すれば、既存問題も上位8手まで揃う。**73局面で20〜40分程度**、KataGo を占有する。やらなくても機能は成立するので、後回しでもよい。

#### B-3. UI: 手順プレイヤーの共通化（`web/js/app.js`）

`renderVariation()` のロジックを `createSequencePlayer()` として切り出す。

- 入力: `{canvas, view, startState, firstColor, pv, comments, size}`
- 表示: `◀`  `3 / 8手`  `▶` ／ 現在の手の一言コメント ／ `最初から` ／ `問題の局面に戻る`
- 盤上は着手を順に置き、取れた石は消す（`goban.js` の既存ロジックを使う）

**練習画面（`viewQuiz`）と詰碁画面（`viewTsumegoQuiz`）の `showResult()` から呼ぶ。**

| 状況 | 出すもの |
|---|---|
| 正解した | 正解手順（best）「この手順で決まります」 |
| 候補手のうちの悪い手を打った | その手の咎め手順 ＋ タブで正解手順に切替 |
| 実戦で打った手と同じ手を打った | punish 手順 ＋ 「これが実戦で打った手です」 |
| 候補外の点を打った | 「AI はこの手を候補にも挙げていません」＋ 正解手順のみ |

手数は最大10手（`pv_max_moves`、FR-08の制約）。`variations.py` の冒頭にある「双方最善の一本道であり、実際の相手が同じに応じるとは限らない」という但し書きを、プレイヤーの下に小さく常時表示する。

#### B-4. 配信データ（`go_review/export.py`）

`problem_payload()` と詰碁の payload に `refutations` を含める。1問あたり最大8手 × 10手 × コメントで、JSONは1問 3〜6KB 程度の増加。73問で **合計 300〜400KB** 増。PWAのプリフェッチ対象なので、`store.js` のキャッシュ挙動は変更不要。

### C. 詰碁を20問前後に増やす

#### C-1. シードの拡充（`go_review/tsumego_seed.py`）

現在の候補は8件（死活3形 × 点対称2 + 両アタリ2）。ここを広げる。

- **テーマを追加**: シチョウ、ゲタ、ウッテガエシ、オイオトシ、欠け眼、攻め合い、ヨセの急所
- **対称変換を4種に**: 今は点対称 `_mirror()` だけ。左右反転・上下反転を加えて最大4倍にする
- **難易度を1〜5に広げる**: 今は2〜4しかない。1手で決まる易しい形と、5手読む形を意図的に入れる
- 候補を **40〜60件** 用意し、既存の判定基準（集中度 `share >= 0.45` かつ 勝率差15pt以上 or 目数差4目以上）で足切りする。**採用率は実測で5〜7割**なので、20〜35問が残る見込み

盤面設計の原則（`tsumego_seed.py` の冒頭コメントに記録されている4回ぶんの失敗）は踏襲する。**盤の上下を黒白で分けて地合いを互角に近づけないと、KataGo が急所を真剣に読まない。**

#### C-2. 詰碁にも咎め手順を付ける

`verify_candidates()` は既に `engine.analyze()` の結果を持っており、`analysis.moves` に候補手とPVが入っている。**追加の解析なしで** B-1 の `refutations` に流し込める。詰碁は盤面が狭く候補が絞れるので、上位8手あればほぼ全部の「押しそうな点」を覆える。

#### C-3. ヒントの拡充

`THEME_HINTS` に新テーマぶんを追加する。2段階（考え方 → 場所の絞り込み）の構成は現行を踏襲。

#### C-4. 実行

```
python -m go_review seed-tsumego
```

KataGo を使うので、**解析バッチが終わってから**回す。候補60件 × 1200 visits で **30〜60分程度**を見込む。
